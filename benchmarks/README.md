# Production browser benchmark: ZaakiyJS vs React and frozen main

**Status: benchmark implementation; no numerical superiority or release claim until CI evidence is reviewed.**

This is a production Vite comparison of the **exact same application semantics** on four variants: React **19.2.4**, ZaakiyJS at immutable main baseline `f19b9f6a466de7f5b03dd085925c8d9092a87f85`, immutable hardening parent `04f453c18b31c7f900d77b037b0548f8888826f1`, and the optimization candidate. React and React DOM are installed only into the isolated benchmark reference app using a committed npm lockfile and `npm ci`; they are never dependencies of ZaakiyJS browser packages. The React fixture uses compiled JSX-runtime calls (`jsx`/`jsxs`), not dev-only React profiling instrumentation. Both apps build under the repository's pinned Vite 6.4.5 and Node 22.

The generated ZaakiyJS apps use the same TypeScript fixture copied into the frozen-main and PR worktrees. The fixture intentionally exercises only the supported **IR v1** subset so comparisons do not rely on newly added compiler features. Both initially render 1,000 keyed rows, a counter, a renameable row, and a conditional visible block. The suite now additionally measures first/last swaps, 1-step rotations, keyed appends/prepends, and middle-item removals/reinsertions, with identical operation definitions in the React and ZaakiyJS fixtures. React uses `memo` and stable keyed rows; ZaakiyJS uses `signal`, `flushSync`, `Show`, `For`. List identity, correct text, row count and conditional behavior are checked before accepting *each sample*. Any mismatch or uncaught exception fails CI.

## Evidence and interpretation

`Production React Benchmark` builds three ZaakiyJS worktrees and the isolated React comparator, serves all four via Vite **preview**, and executes pinned Playwright in Chromium, Firefox and WebKit. Each browser/framework gets a fresh page, 10 warmups and 50 measured iterations per operation. Sparse operations use eleven alternating changes per timing sample when compatible with a single final expected transition, avoiding false zero-millisecond readings from coarse browser clocks. Reversal and rotation remain single operations. The reference execution order rotates deterministically by browser engine to reduce fixed-order bias. Counter (101), rename (41) and toggle (81) use odd repeated synchronous updates per sample, reported as **milliseconds per update**, to overcome coarse Firefox/WebKit timer quantization; keyed reverse runs once per sample. Original DOM element identity is asserted for every retained row on every operation, including swap, rotate, insertion and deletion. Every operation is checked against an exact expected key order and expected visible/label/counter state. `performance.now()` brackets only the synchronous update and settled DOM, excluding Playwright roundtrip; results include raw samples, p50, interpolated p95/p99, dispersion, mean, startup mark, optional uncontrolled JS heap (where browser reports it), exact browser versions, commit SHA and runner environment. Separate JSON computes per-production-asset raw, gzip and Brotli JS/CSS transfer sizes; it excludes source maps and build tooling.

`benchmark-artifacts/browser-results.json` and `benchmark-artifacts/bundle-sizes.json` are uploaded even when another job step fails. Never treat an absence of evidence, one browser, or a failed sample as passing. Run IDs and artifacts must match the **exact candidate head** before review. Compare candidate to both frozen main and React with the same browser, workload and build settings.

**Important limitations:** React compilation uses direct `jsx`/`jsxs` calls rather than an additional Babel/React Compiler optimization pipeline. The chosen components are intentionally narrow; these numbers do **not** generalize to routing, SSR, hydration, network, forms, enterprise apps or different browser hardware. `performance.memory` is non-standard and cannot certify leak freedom. A mounted-start mark measures JS-to-mount completion and should not be called LCP/FCP. Multi-machine baselines and independent end-user benchmarks still require work.

## Merge policy

The first baseline comparison (PR head `a988b19a`) established targeted high-churn reverse and bundle regression thresholds. CI gates **1,000-row reverse p95** against the tightest of (React p95 × 2 + 10 ms), (frozen-main p95 × 1.5 + 10 ms) and (frozen hardening p95 × 1.25 + 2 ms) on each browser. Five sparse keyed operations additionally reject a p95 above (frozen hardening p95 × 1.5 + 2 ms). All nine workloads and raw-sample counts are mandatory, even when only a subset has calibrated latency limits. Emitted app JS/CSS gzip is checked against the tighter of (main × 1.10 + 512 bytes) and (hardening × 1.05 + 512 bytes). These deliberately bounded, noisy-runner-tolerant thresholds apply **only to this fixture**; they are not a blanket performance certification. CI also gates build completion and functional equivalence. After a set of repeated green baseline runs, refine regression budgets with documented variance, environment, p50/p95 and CI failure tolerance. Do not overfit limits to a single lucky run. Do not silently infer production readiness, publish a ranking, weaken correctness assertions or set an uncalibrated threshold just to get green checks. The broader M6 memory/CPU/size and real-world app certification remains open.

To reproduce, follow `.github/workflows/production-benchmark.yml` using Node 22, pnpm 10.20.0, Vite 6.4.5, Python 3.12 and Playwright 1.64.1. Exact commands and baseline source revision are checked in to the workflow.
## Expansion phase

Nine comparable operations are available. The committed `regression-gate.mjs` requires full evidence for all nine workloads, applies broad reverse and sparse-operation guards, and checks output size. Small-operation submillisecond differences remain diagnostic until statistically calibrated on multiple independent machines. The failure-injection tests verify that missing evidence and large genuine regressions fail CI. Do not claim that one passing CI run certifies all nine operations, 10k list scaling, real-user startup or memory. Browser-engine-specific regressions must be investigated without substituting user-agent branching for a validated algorithm.
## Before/after and package-level attribution

The fourth comparison variant is the exact head of the original hardening PR #61. Its unchanged package implementations are the control for **incremental performance work**, distinct from frozen main (which lacks multiple legitimate hardening features). All candidate optimization claims must compare against this **hardening** reference as well as main and React.

The separate `package-sizes.json` inventory records emitted JS/CSS size across all **23 packages** against both ZaakiyJS references. It sums individually gzip- or Brotli-compressed package files, **not** browser transfer size, retained memory, fully tree-shaken runtime size, nor an npm tarball. The emitted app fixture JS/CSS remains independently reported in `bundle-sizes.json`.

`core-{main,hardening,candidate}.json` measures repeated creation/disposal of 2,000 child owners and validates exact cleanup counts. `compiler-{main,hardening,candidate}.json` measures the supported common TSX fixture, validates diagnostics and SHA-256 output determinism. `signals-{main,hardening,candidate}.json` captures each immutable source's existing 1,000-fanout / 5,000-update benchmark. These are synthetic diagnostics, not interchangeable with browser interactive performance or independently certified memory retention.

The benchmark's expanded parity assertions are blocking even if measured times are faster. Reported initial-mount marks are not LCP/FCP. Additional CI regression budgets should only become blocking after independent calibration runs establish an appropriate statistical and timer-resolution floor.

## Router optimization microbenchmark

`microbench-router.mjs` runs a 514-route table with two parameterized nested levels and 16,000 timed path matches per variant. It validates inherited params, route identity and non-inheritance of leaf-only params on each iteration. The candidate router avoids reparsing every parent route prefix during matching, and treats reserved parameter names as own data properties rather than prototype setters. The JSON is diagnostic until repeated measurements establish realistic regression budgets. This does not measure asynchronous navigation, component mount, loaders or code splitting.

The workflow also runs a pinned nightly benchmark. The scheduled results are diagnostic and do not imply that individual package optimization work or release certification is complete.
